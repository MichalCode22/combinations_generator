# מחולל הקומבינציות | Combinations Generator

אפליקציית Web (שרת + לקוח) שמחוללת את כל התמורות (permutations) של המספרים `1..n`, כאשר `n` הוא מספר שלם בין 1 ל-20, בסדר **לקסיקוגרפי עולה**.

מספר התמורות עבור `n = 20` הוא 2,432,902,008,176,640,000, ולכן **שום תמורה לא מחושבת מראש**: כל קריאה לשרת מחשבת רק את מה שהיא צריכה, וכל החישוב מתבצע בשרת. הלקוח אחראי על תצוגה, ולידציית קלט וחישובי דפדוף בלבד.

| | |
|---|---|
| שרת | ASP.NET Core, .NET 8 |
| לקוח | Angular 20 (standalone components, signals, OnPush, zoneless) |
| בדיקות | xUnit + FluentAssertions, Karma/Jasmine, Playwright |

## תכונות

- הזנת `n` (עם ולידציה בלקוח ובשרת) והצגת "סה"כ האפשרויות לסדר n מספרים בשורה הוא: X", כאשר X מוצג עם מפרידי אלפים.
- **הבא:** מציג את התמורה הבאה ואת המספר הסידורי שלה, למשל `קומבינציה מספר 1 – [1,2,3]`. בסיום מוצגת ההודעה "אין יותר קומבינציות".
- **כל הקומבינציות:** תצוגה מדופדפת (Pagination בצד השרת) שמתחילה מהתמורה שאחרי האחרונה שהוצגה. כוללת דף הבא, דף קודם, מספרי דפים, קפיצה לדף מסוים, קפיצה לראשון ולאחרון, ובחירת גודל דף (10/20/50/100).
- **חזור:** חזרה למצב הרגיל, עם התמורה האחרונה שהוצגה בתצוגת הדפדוף. "הבא" ממשיך מיד אחריה.
- **איפוס:** חזרה למסך הראשון והזנת `n` מחדש. ה-session נמחק בשרת.
- בידוד מלא בין משתמשים: לכל משתמש session משלו בשרת.
- ממשק בעברית, RTL. התמורות מוצגות ב-`dir="ltr"` כדי שהסוגריים והפסיקים יוצגו נכון.

- **E2E:** `n = 3`, `n = 1`, `n = 20` (כולל קפיצה לדף האחרון), וזרימה מלאה: הבא ×2, כל הקומבינציות, חזור, הבא.

## תיעוד ה-API

כל הקריאות, חוץ מ-`start`, דורשות את ההדר `X-Session-Id` שמתקבל מ-`start`. הנתיב הבסיסי: `/api/combinations`.

| פעולה | מתודה ונתיב | תשובה |
|---|---|---|
| StartAPI | `POST /start` | `200` |
| GetNextAPI | `POST /next` | `200` |
| GetAllAPI | `GET /all?pageSize=&page=&enter=` | `200` |
| תמורה נוכחית | `GET /current` | `200` |
| איפוס | `DELETE /` | `204` |

> **מספרים גדולים:** `total`, `index`, `page`, `totalPages` ו-`startIndex` מוחזרים כ**מחרוזות** (JSON strings), כי הם חורגים מ-`Number.MAX_SAFE_INTEGER` של JavaScript. הלקוח מפענח אותם ומחשב איתם ב-`BigInt`. איברי התמורה עצמם הם מספרים רגילים.

### StartAPI: התחלת session

```http
POST /api/combinations/start
Content-Type: application/json

{"n":3}
```

```json
{"sessionId":"b4e0f2df-8c2f-43ab-bb1b-7ee6b3d9d84f","total":"6"}
```

### GetNextAPI: התמורה הבאה

```http
POST /api/combinations/next
X-Session-Id: b4e0f2df-8c2f-43ab-bb1b-7ee6b3d9d84f
```

```json
{"hasMore":true,"index":"1","permutation":[1,2,3],"message":null}
```

אחרי התמורה האחרונה, וגם בכל קריאה חוזרת אחריה, התשובה זהה והמצב לא משתנה:

```json
{"hasMore":false,"index":null,"permutation":null,"message":"אין יותר קומבינציות"}
```

### GetAllAPI: דפדוף בכל הקומבינציות

```http
GET /api/combinations/all?pageSize=20&page=1&enter=true
X-Session-Id: b4e0f2df-8c2f-43ab-bb1b-7ee6b3d9d84f
```

| פרמטר | משמעות |
|---|---|
| `pageSize` | מספר פריטים בדף, בין 1 ל-100 (ברירת מחדל 10) |
| `page` | מספר הדף, החל מ-1, **יחסית לנקודת ההתחלה `allStart`** |
| `enter` | `true` בכניסה לתצוגה: מקבע `allStart = lastShownIndex + 1`. בכל כניסה מחדש הנקודה מחושבת מחדש. בקריאות דפדוף (`enter=false`) נשמרת אותה נקודת התחלה |

```json
{
  "items": [{"index":"1","permutation":[1,2,3]}],
  "page": "1",
  "totalPages": "1",
  "startIndex": "1",
  "total": "6",
  "message": null
}
```

אם לא נותרו תמורות, התשובה היא `200` עם `items` ריק, `totalPages: "0"` וההודעה "אין יותר קומבינציות".

אחרי כל קריאה מוצלחת, התמורה האחרונה בדף שהוחזר נשמרת כ"אחרונה שהוצגה". לכן `Current` (ו"חזור") מחזיר אותה, ו-`Next` ממשיך מיד אחריה.

### תמורה נוכחית

```http
GET /api/combinations/current
X-Session-Id: b4e0f2df-8c2f-43ab-bb1b-7ee6b3d9d84f
```

```json
{"index":"2","permutation":[1,3,2]}
```

אם עדיין לא הוצגה אף תמורה: `{"index":null,"permutation":[]}`.

### איפוס

```http
DELETE /api/combinations
X-Session-Id: b4e0f2df-8c2f-43ab-bb1b-7ee6b3d9d84f
```

מסיר את ה-session מהשרת ומחזיר `204`.

## ולידציה ושגיאות

כל השגיאות מוחזרות כ-`ProblemDetails` (RFC 7807, `application/problem+json`).

| תנאי | תוצאה |
|---|---|
| `n` אינו מספר שלם בין 1 ל-20 (כולל `3.5`, `"abc"`, `null`, גוף חסר, מספר ענק) | `400` |
| `pageSize` מחוץ ל-1..100 | `400` |
| `page` קטן מ-1, גדול מ-`totalPages`, לא מספרי או גדול מ-`ulong` | `400` |
| `X-Session-Id` חסר, לא תקין, לא מוכר או שפג תוקפו | `404` |
| הגעה למכסת ה-sessions הפעילים | `503` |
| חריגה לא צפויה | `500` (עם `ProblemDetails` כללי) |

הלקוח מטפל ב-`404` על ידי חזרה למסך הראשון עם הודעה ידידותית ("פג תוקף המפגש. התחילו מחדש.").

## החלטות תכנון

- **סדר:** לקסיקוגרפי עולה (`[1,2,3]`, אחר כך `[1,3,2]`). בנוסח המטלה הדוגמה הראשונה מציגה סדר יורד והשנייה סדר עולה, ובחרתי בעולה.
- **אין חישוב מראש:** `GetNext` מחשב רק את הצעד הבא (`NextPermutation`). `GetAll` מחשב כל פריט בדף ישירות לפי האינדקס שלו (`Unrank`), ולכן אפשר לקפוץ לכל דף, כולל האחרון.
- **ניהול מצב:** ה-state נשמר בשרת, לכל משתמש בנפרד, לפי מזהה session (GUID) שהלקוח שולח בהדר `X-Session-Id`. ב-session נשמרים `n`, המספר הכולל, אינדקס התמורה האחרונה שהוצגה, התמורה הנוכחית ונקודת ההתחלה של תצוגת "כל הקומבינציות". תפוגה "מחליקה" (sliding expiration, 30 דקות), מכסה של 10,000 sessions פעילים, ועדכון אטומי לכל session.
- **מספור דפים:** הדפדוף יחסי לנקודת ההתחלה `allStart`, ולכן הדף הראשון מתחיל תמיד מהתמורה שאחרי האחרונה שהוצגה, גם אם הוצגו כבר 1,000 תמורות במצב הרגיל.
- **שינוי גודל דף:** הלקוח שומר על מיקום הפריט הראשון שמוצג, כלומר מחשב את הדף החדש לפי הפריט הראשון בדף הנוכחי.
- **סנכרון בין המצבים:** אחרי כל דף, התמורה האחרונה בו נשמרת כתמורה האחרונה שהוצגה. לכן "חזור" מציג אותה, ו"הבא" ממשיך מיד אחריה.
- **מספרי ענק:** כל המספרים הגדולים עוברים כמחרוזות ב-JSON, והלקוח מחשב אותם עם `BigInt` (כולל לוגיקת ה-Pager, שמוגבלת לחלון קבוע של מספרי דפים עם נקודות המשך, כך שלא נוצרים מיליוני כפתורים).
- **גודל דף:** מקסימום 100, ברירת מחדל 10.
- **Git:** `.gitignore` בשורש הפרויקט מתעלם מתוצרי build, תלויות, תוצאות בדיקה וקובצי סביבה מקומיים.
- **הפשטת האחסון:** `ISessionStore` הוא ממשק ב-Application, כדי שאפשר יהיה להחליף את האחסון (למשל ל-Redis) בלי לשנות את שאר השכבות.
- **מצב בלקוח:** `CombinationsStore` מבוסס Signals, עם שלושה מצבים (`start`, `single`, `all`). מזהה ה-session נשמר בזיכרון בלבד, ולכן רענון הדף מחזיר למסך ההתחלה.

## תשובות לשאלות

### 1. מהו מודל ניהול ה-State שבחרת ולמה?

ה-state נשמר **בשרת, לכל משתמש בנפרד**: בהתחלה נוצר session עם מזהה (GUID), והלקוח שולח אותו בהדר `X-Session-Id` בכל קריאה. ב-session נשמרים `n`, המספר הכולל, אינדקס התמורה האחרונה שהוצגה, התמורה הנוכחית ונקודת ההתחלה של תצוגת "כל הקומבינציות".

בחרתי בזה כי המטלה דורשת שכל החישוב יתבצע בשרת, ורק השרת יודע מה הייתה התמורה האחרונה. כך `GetNext` יודע להמשיך מהמקום הנכון, ו-`GetAll` מתחיל מהמקום הנכון. הגישה נותנת בידוד בין משתמשים, ובנוסף `ISessionStore` מאפשר להחליף את מנגנון האחסון בלי לשנות את שאר הקוד.

בלקוח נשמר רק מצב תצוגה (איזה מסך מוצג, `n`, התמורה הנוכחית, מצב הדפדוף), ב-service קטן מבוסס Signals. הנתונים הם מצב אפליקציה פשוט ולכן לא נדרשת ספריית State כבדה.

### 2. מה ההבדל בין NextPermutation לחישוב Permutation-Based-Index, ומתי בחרת בכל אחד?

- **`NextPermutation`** מקבל את התמורה הנוכחית ומחשב את זו שאחריה בסדר לקסיקוגרפי: מוצאים את האיבר שצריך להגדיל (pivot), מחליפים אותו עם העוקב הקטן ביותר מימינו, והופכים את הסיומת. זה O(n) לצעד אחד, אבל הוא תלוי במצב הקודם וצועד רק קדימה.
- **חישוב לפי אינדקס (`Unrank`)** מקבל מספר סידורי `k` ומחזיר ישירות את התמורה במקום ה-`k`, בעזרת מערכת הפקטוריאל (Lehmer code): כל "ספרה" קובעת איזה מהאיברים שנותרו נבחר, וגודל הבלוק הוא `(n-i-1)!`. הוא לא תלוי בתמורות הקודמות. הפעולה ההפוכה היא `Rank`.

השימוש בפועל:

- ב-**`GetNext`** השתמשתי ב-`NextPermutation`, כי צריך רק את הצעד הבא, וה-session ממילא שומר את התמורה הנוכחית.
- ב-**`GetAll`** השתמשתי ב-`Unrank` לכל פריט בדף, כי כך אפשר לקפוץ ישירות לכל דף (כולל האחרון) בלי לעבור על מה שלפניו. העלות זניחה: לכל היותר 100 פריטים בדף, וכל `Unrank` הוא O(n²) עם n ≤ 20. אפשר היה לבצע `Unrank` רק לפריט הראשון ולמלא את השאר ב-`NextPermutation` (O(n) לכל פריט), אבל התועלת קטנה והקוד פשוט יותר כך.

### 3. אם 3 משתמשים שונים נכנסים בו-זמנית, איך המערכת תתנהג ולמה?

כל משתמש מקבל session משלו, עם `n`, אינדקס ותמורה נוכחית משלו, ולכן הרצפים שלהם **בלתי תלויים לחלוטין**: משתמש אחד יכול להיות ב-`n=3` ואחר ב-`n=20`, בלי הפרעה. אין שדות סטטיים משתנים: ה-store הוא singleton, אבל הוא רק מחזיק מילון של sessions, וה-`PermutationGenerator` חסר מצב ובטוח לשימוש מקבילי.

לכל session יש נעילה (`SemaphoreSlim`) משלו. בקשות מקבילות של אותו משתמש (למשל לחיצות כפולות) מסודרות בתור ומבוצעות אחת אחרי השנייה, כך שלא נוצרות כפילויות או חורים במספור. בקשות של משתמשים שונים לא חוסמות זו את זו. רק יצירת session חדש עוברת דרך נעילה קצרה משותפת, כדי לאכוף את מכסת ה-sessions. ההתנהגות נבדקה בבדיקות: 50 sessions מקבילים, ו-100 קריאות `Next` מקבילות על אותו session שהחזירו כל אינדקס בדיוק פעם אחת.

### 4. אם נרצה להוסיף שמירה ל-Redis, אילו 2 שינויים תעשה בצד השרת?

1. **מימוש חדש של `ISessionStore`** (למשל `RedisSessionStore`) שמשמר את ה-session ב-Redis בסריאליזציית JSON, תחת מפתח כמו `session:{guid}`, עם TTL שמתחדש בכל גישה ומחליף את תפוגת ה-sliding של האחסון בזיכרון. רושמים אותו ב-DI לפי הגדרה ב-`appsettings`. שאר השכבות לא משתנות, כי הן תלויות רק בממשק. מכסת ה-sessions תצטרך להיות מוגדרת מחדש (למשל מונה ב-Redis), כי אי אפשר לספור sessions במילון מקומי.
2. **החלפת הנעילה המקומית בעדכון אטומי מבוזר.** `SemaphoreSlim` מגן רק בתוך תהליך אחד, וכששרתים מרובים כותבים לאותו session הוא לא עוזר. הפתרון: נעילה מבוזרת לכל session (למשל `SET NX PX`), או עדכון אופטימי עם שדה גרסה וסקריפט Lua או `WATCH`, שמבצע קריאה, חישוב וכתיבה כפעולה אחת ומנסה שוב בקונפליקט. החתימה הקיימת `UpdateAsync(sessionId, update)` כבר מתאימה לזה, כי כל שינוי מצב עובר דרכה.

### 5. מה החיסרון העיקרי של NextPermutation עבור n=20?

אין גישה ישירה. כדי להגיע לתמורה במקום ה-`k` צריך לבצע `k` צעדים, ויש כ-2.4×10¹⁸ אפשרויות, כך שאי אפשר להגיע לדף רחוק, ובוודאי לא לסוף. גם אם כל צעד לוקח מיקרו-שנייה, ההגעה לאמצע הרצף תיקח עשרות אלפי שנים. בנוסף, הוא תלוי במצב הקודם, ולכן אי אפשר לחשב דפים במקביל או לשחזר מצב מאינדקס בלבד. לכן ב-`GetAll` נדרש `Unrank`, שמגיע לכל מקום ב-O(n²) ללא תלות ב-`k`.

## מגבלות וכיווני המשך

- ה-sessions נשמרים בזיכרון בלבד: הם אובדים באתחול שרת, ואי אפשר להריץ כמה מופעי שרת (ראו תשובה 4).
- ניקוי sessions שפג תוקפם מתבצע ביצירת session חדש ובגישה אליהם. אפשר להוסיף שירות רקע לניקוי תקופתי.
- מזהה ה-session נשמר בזיכרון הלקוח, ולכן רענון הדף מחזיר למסך ההתחלה. אפשר לשמור אותו ב-`sessionStorage`.
- אין אימות משתמשים. מזהה ה-session הוא הסוד היחיד, וקשה לנחש אותו כי הוא GUID.
